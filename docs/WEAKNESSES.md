# 약점 · 우회 방법 · 한계 (Known weaknesses & bypasses)

이 저장소의 모든 클라이언트 측 방어는 **숙련된 분석가 앞에서는 결국 뚫립니다.**
AI 자동화 도구(REA 류)는 이 한계를 바꾸지 못하지만, 뚫는 데 걸리는 *시간과 숙련도*를
크게 낮춥니다. 아래는 각 기법이 정확히 어떻게 무력화되는지와, 그럼에도 남는 가치입니다.
현실적인 기대치를 갖고 레이어를 겹치세요.

## 공통 진실 (먼저 읽기)
- **메모리 덤프 앞에서 문자열/상수 은닉은 전부 무의미.** 복호화된 평문은 결국 메모리에 뜬다.
- **결과가 boolean 분기인 모든 체크는 패치 가능.** `if (detected)` 한 줄을 NOP 하면 끝.
- **단일 지점 체크는 즉사.** 한 함수에 몰린 검사는 브레이크포인트 한 번에 발각·제거된다.
- **유일하게 내구성 있는 보호는 세 가지뿐:** (1) 비밀·핵심 로직을 서버에 두기, (2) 크랙의
  경제적 이득을 없애기(SaaS·서버 검증 라이선스), (3) 잦은 업데이트로 크랙을 무효화.

## 네이티브 (C/C++)

| 기법 | 우회 방법 | 남는 가치 |
|------|-----------|-----------|
| ptrace self-trace / TracerPid | 체크 분기 패치, `LD_PRELOAD`로 `ptrace`/`fopen` 후킹해 `/proc` 위조 | 자동 디버거 attach를 한 번 걸러줌 |
| IsDebuggerPresent / PEB | ScyllaHide 등으로 모든 표준 체크 무력화, PEB 플래그 패치, 하드웨어 BP는 플래그 미설정 | 초보적 디버깅만 차단 |
| Frida `/proc/self/maps` 스캔 | gadget 리네임, `fopen`/`read` 후킹으로 maps 필터링, embedded 모드, anti-anti-frida 스크립트 | 기본 Frida 세션 탐지 |
| 실행파일 자가 해시 | **메모리 패치는 탐지 못 함**(디스크 원본 그대로), 해시 함수 자체를 후킹해 기대값 반환, 비교 분기 패치 | 디스크 변조·재배포 탐지 |
| 컴파일타임 XOR 문자열 | 복호화 직후 BP 걸고 메모리에서 평문 読取, XOR 키가 바이너리에 존재 | `strings`/정적 grep만 차단 (런타임 무력) |
| strip / OLLVM 난독화 | 디컴파일러+AI가 구조 복원, OLLVM 전용 디옵스큐에이터 존재, VMProtect도 전문가가 분석 | 읽는 비용 대폭 상승 |

**핵심 약점:** 자가 해시는 *디스크*만 본다. 실행 중 메모리 `.text` 패치는 못 잡는다 →
in-memory 해시를 병행해야 하고, 그마저 해시 함수 후킹으로 뚫린다.

## Electron / JavaScript

| 기법 | 우회 방법 | 남는 가치 |
|------|-----------|-----------|
| bytenode (V8 바이트코드) | V8 바이트코드 디스어셈블러·디컴파일러 존재, `Module`/`vm` 후킹으로 소스 덤프, V8 버전 고정 취약 | 평문 소스 즉시 노출은 방지 |
| javascript-obfuscator | de4js 등 디옵스큐에이터+AST 도구로 대부분 복원, `selfDefending`/`debugProtection`만 제거 가능 | 캐주얼 분석 지연 |
| Electron fuses | `asar`는 정적으로 여전히 추출됨, fuses는 run-as-node 경로만 차단, 구버전/패치된 Electron으로 우회 | node 덤프 공격 차단 |
| devtools 타이밍 가드 | 렌더러 JS에서 체크 한 줄 삭제, 원격 디버깅, 그냥 `debugger` 제거 | 비개발자 차단 수준 |

**핵심 약점:** Electron은 구조상 최약체. `asar` 추출은 못 막고, bytenode도 "난독화"지
"암호화"가 아니다. 비밀은 절대 두지 말 것.

## Android

| 기법 | 우회 방법 | 남는 가치 |
|------|-----------|-----------|
| Kotlin 디버거/루트/에뮬 탐지 | smali 패치, Frida 후킹으로 `false` 반환, Magisk Hide/Zygisk DenyList로 루트 은폐, `Build` 속성 위조 | 기본 환경 1차 필터 |
| 서명(재패키징) 검증 | 체크를 patch 하거나 `PackageManager` 후킹, Java에만 있으면 즉시 제거 | 단순 재서명 탐지 |
| Network Security Config 피닝 | 루팅+Frida universal SSL unpinning, objection, Magisk 모듈, APK 내 config 패치, Magisk로 사용자 CA 주입 | 비루팅 기기 MITM 차단 |
| R8 난독화 | 이름만 바뀜, JADX가 읽기 쉬운 코드로 복원 | 심볼 가독성만 저하 |

**핵심 약점:** 루팅된 기기에서는 Frida universal unpinning 스크립트 하나로 피닝이 통째로
무력화된다. Kotlin 레벨 체크는 Frida 스크립트가 가장 먼저 노리는 표적.

## .NET (C#)

| 기법 | 우회 방법 | 남는 가치 |
|------|-----------|-----------|
| `Debugger.IsAttached` | dnSpy로 한 줄 패치, 후킹 | 초보 디버깅 차단 |
| 어셈블리 자가 해시 | 메모리 패치 미탐지, single-file/AOT에서 `Location` 공백, 해시 후킹 | 디스크 변조 탐지 |
| ConfuserEx | 공개 디옵스큐에이터/언패커 존재(de4dot 계열), anti-tamper 돌파 사례 다수 | 비용 상승, 비밀 보호는 아님 |

**핵심 약점:** .NET IL은 전 플랫폼 중 가장 쉽게 디컴파일된다. 중요 로직은 네이티브 DLL로
빼거나(P/Invoke), 서버로 옮기거나, NativeAOT로 IL 자체를 없애야 한다.

## 그래서 어떻게 설계해야 하나
1. 이 도구들은 **"시간 벌기 + 자동화 공격 차단"** 용도. 비밀 저장소가 아니다.
2. 반드시 **서버 측 검증**과 함께 쓴다. 클라이언트 체크 결과를 서버가 신뢰하면 안 된다.
3. 체크는 **분산 + 간접 반응**(지연·상태 오염)으로. 즉시 종료는 체크 위치를 알려주는 꼴.
4. **경제성**이 최종 방어선: 크랙해도 얻을 게 없게 만들면(서버 종속) 공격 동기가 사라진다.
